# Археологический аудит корпуса E-Continuity

Дата аудита: 2026-07-26. Вход: 17 ZIP‑архивов, предоставленных автором. Метод: рекурсивное чтение ZIP/TAR до глубины 5, фиксация цепочки контейнеров и исходного пути, SHA‑256 каждого payload, исключение AppleDouble/`__MACOSX` из содержательной статистики, дедупликация по хешу.

## 1. Количественная карта

| Показатель | Значение |
|---|---:|
| Внешние ZIP | 17 |
| Записи во всех контейнерах | 3 073 |
| Содержательные записи без macOS‑метаданных | 2 606 |
| Уникальные payload по SHA‑256 | 344 |
| Группы точных дублей | 306 |
| Уникальные текстоаудируемые файлы | 280 |
| Проверенные строки/абзацы/строки таблиц | 24 358 |
| Ошибки извлечения DOCX/PDF/TXT/MD | 0 |

Вывод: корпус является не набором 2 606 независимых документов, а 344 уникальными объектами, многократно вложенными в сборки, reviewer‑пакеты, PDF‑only экспорты и резервные архивы. Управлять им на уровне имён файлов нельзя; canonical identity должна задаваться SHA‑256 + document UID + статусом версии.

## 2. Реконструированная хронология

1. **v1.0–v1.3** — ранняя узкодоменная и эссеистическая стадия; появляются OAIS‑ориентиры, биобанк и первые кейсы.
2. **v2.1** — Full Technical Edition с 13‑компонентной формулой, цепью continuity, уровнями recoverability и набором метрик‑кандидатов.
3. **v2.2** — добавлены Activation Failure, три уровня proof testing и aerospace‑кейс; сформированы full master/reviewer/PDF‑only пакеты.
4. **v2.3** — стабилизационный патч: 13 компонентов свернуты в 5 блоков, введена MVW v0.1, смягчён статус CASE‑SPACE‑001.
5. **После PROJECT_NAME_LOCK** — основное имя меняется с Template E на E‑Continuity. README объявляет v2.3 содержательно текущим, но с устаревшим названием; v2.3.1 планируется как rename‑only.
6. **Структурированный снимок 2026‑06‑05** — появляется файловая архитектура `E_CONTINUITY`, реестры правил, очередь интеграций и migration note. Это наиболее зрелый навигационный слой, но не новый содержательный релиз.

## 3. Статусные зоны

| Зона | Решение |
|---|---|
| CURRENT | v2.3 как содержательное ядро, с обязательным применением Stabilization Patch |
| WORKING | правила/очередь интеграций от 2026‑06‑05 и подготовка v2.3.1 |
| REVIEW | reviewer packages и материалы внешней оценки; не считать независимой валидацией |
| LEGACY | v1.x, v2.1, v2.2 и `OLD_DO_NOT_EDIT`; только чтение |
| RAW | заметки, изображения, найденные сторонние проектные файлы; не включать в релиз без явного решения |

## 4. Археологические дефекты

- **AR-001 — дублирование контейнеров.** Одни и те же payload повторяются во внешних и вложенных ZIP. Риск: исправление одной копии не меняет остальные.
- **AR-002 — имя не определяет версию.** Суффиксы `(1)`, `(2)`, `(3)` отражают копирование, а не семантическую ревизию.
- **AR-003 — рассинхрон бренда и релиза.** Активное имя E‑Continuity сосуществует с canonical package, названным Template E v2.3.
- **AR-004 — v2.3 включает исторические слои.** Full Technical Edition продолжает показывать заголовок v2.1 и addendum‑структуру; патч v2.3 корректирует документ снаружи.
- **AR-005 — смешаны source, export и review.** DOCX/MD/PDF и unified PDF представлены рядом без однозначного источника истины.
- **AR-006 — публичность против режима private.** Внутренние документы запрещают передачу третьим лицам, тогда как целевой GitHub‑репозиторий публичен. Нужна явная публикационная политика.
- **AR-007 — provenance не равен верификации.** Карточки происхождения полезны, но ряд из них прямо говорит `GENERATED_FROM_CURRENT_DIALOGUE` и `UNVERIFIED`; такие файлы нельзя повышать до первичного источника.

## 5. Canonical release set (рекомендация)

Для следующего релиза оставить один источник каждого класса:

1. `README_CURRENT` / release status.
2. `01_Full_Technical_Edition_RU` как единый редактируемый source.
3. `09_Stabilization_Patch_v2_3_RU` — после интеграции удалить как внешний патч и оставить changelog.
4. Case Library, Operational SOP Pack, Glossary, Boundary Conditions.
5. References с claim‑to‑source matrix.
6. Reviewer package, собранный автоматически из canonical sources.
7. Manifest + SHA‑256, вычисленные после сборки.

PDF, unified PDF и ZIP должны быть производными build‑артефактами, а не редактируемыми источниками.
